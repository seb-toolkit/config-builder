How to do a test run of your Safe Exam Browser exam

Published 2026-11-26 · Unofficial guide

The best protection against exam-day problems is a proper rehearsal. This guide describes a test run for a Moodle quiz in Safe Exam Browser (SEB). Allow a few days for it, so you can fix what you find.

1. Test as a student, not as a teacher

This is the step people miss. In Moodle, teachers and managers usually have a permission that lets them bypass the Safe Exam Browser requirement, so a quiz that opens fine for you in a normal browser may be locked to everyone else. Check this on your own installation, then:

  • Make a test student account, enrol it in the course and use it for every test. A separate, real test account is the most reliable way to see what students see.
  • Use a copy of the quiz with the same settings, in a test course or with access limited to your test users, so real students do not see it.

2. Cover every kind of computer

Try the exam on each combination students will use, and record the result for each.

ComputerCheck
A lab or cluster computerSEB installed, correct version, launches from the quiz page.
Windows laptop (BYOD)Fresh install of the current SEB; Windows Hello or phone sign-in if used.
MacSEB in the Applications folder; sign-in method that works on a Mac.
iPad, if allowedThe App Store version; settings that apply only to some systems.
A computer with the quirks you expectTwo screens, a managed laptop with a firewall or proxy, a slow connection.

3. The checklist for each test

  1. Start. The quiz launches from the Launch Safe Exam Browser button. Opening the quiz in a normal browser is refused.
  2. Sign in. The method students will really use works, including the phone approval prompt. See Microsoft sign-in in SEB.
  3. Allowed. Everything the exam needs works: question types, images, embedded video, equation tools, file uploads, any other site you allowed.
  4. Blocked. Pages you meant to block are blocked: another website, the Moodle dashboard and menu, a link inside a question. Try the address bar if you enabled one. Use the website test in the builder to check a list of addresses.
  5. Windows. The quiz stays in one window, and a link that asks for a new window does not escape your rules. Check the quiz's Moodle browser security is None.
  6. Programs and keyboard. Another application cannot be opened, and copy and paste behaves as you set it.
  7. Downloads and uploads. Where files go, and whether a student can find them to upload. See downloads and uploads.
  8. Finish and quit. Submit, then leave by your intended route: quit password, Exit Safe Exam Browser button or quit link. Check that quitting during the attempt is not possible if you do not want it to be.
  9. Review. Look at the attempt as a teacher: answers saved, time recorded, anything strange in the logs.

4. Try the things that go wrong

  • Network drops. Turn Wi-Fi off for 30 seconds, then on. Does the quiz recover, and are answers kept?
  • Restart. Close SEB mid-attempt and re-launch from Moodle. Does the attempt continue, and what happens to the timer?
  • Wrong or old SEB. Install an older version or open the quiz with a different browser. Is the message clear, and does your server refuse it?
  • Closed programs. Start with screen sharing or a restricted program running. What does a student see?
  • Accessibility. Try the tools your students use (screen reader, magnification, extra time). Some assistive tools conflict with lockdown, so find out in advance.

5. Pilot with a few real students

A practice quiz in SEB, taken by real students on their own computers about a week before the exam, finds problems that you cannot. Ask them to report their computer type, the SEB version and anything odd. Give them the student guides and the student checklist.

6. Rehearse the room

  • Run through the invigilator sheet (the builder makes one) with the people who will use it.
  • Know who handles a student who cannot start, and what the options are: another computer, another room, or an alternative arrangement.
  • Decide in advance how the clock is handled when something fails.

7. Go or no-go, and freeze

  • Note the SEB versions you tested and the .seb file you used. Keep a copy.
  • Freeze the settings a day or two before. A change after testing is an untested change.
  • If a core test failed on a main computer type, fix it or use another route. Do not hope it works on the day.
  • Keep a plan B: a spare computer, a paper copy or a second room.
