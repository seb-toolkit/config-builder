SEB Server: logging student activity, where to host it, and what happens behind a firewall

Published 2026-11-26 · Unofficial guide

Safe Exam Browser (SEB) can record some of what students do and send it to a central server, but only through a separate piece of software called SEB Server. Neither a plain .seb file nor Moodle's Safe Exam Browser setting does this on its own. This guide explains what SEB records, how it connects, where the server can run, and what happens when a firewall gets in the way. It is based on the SEB for Windows source code and the SEB Server setup documentation as of November 2026. I have not run a production SEB Server, so test everything on your own network.

What SEB records without a server

  • A local log. SEB keeps a log on the student's computer, with a setting for the folder (enableLogging, logDirectoryWin and logDirectoryOSX). SEB's help text describes it as useful for debugging and for finding possible manipulation. Nothing sends it anywhere by itself.
  • Web addresses in that log. A setting controls how SEB shows and logs addresses (browserWindowShowURL). Set to "never", URLs are neither shown nor logged.
  • Moodle. Moodle's Safe Exam Browser plugin checks settings and keys. I found no logging of student web activity in it. Moodle's own logs show activity inside Moodle, such as quiz attempts.

What SEB Server adds

  • Regular pings at a set interval, so invigilators can see who is connected.
  • Log events, queued by the client and sent in batches on a timer.
  • Status of the network connection and the power supply.
  • Messages in both directions: students can raise a hand, and invigilators can lock a screen or end a session. The client confirms each instruction.
  • Screen proctoring (optional). With a Screen Proctoring service, SEB takes screenshots at set intervals and can attach metadata: the active program, the window title and the web address. These settings (screenProctoringMetadataURLEnabled and its siblings) can only be configured through SEB Server, according to SEB's help text. It is a separate service from the main server.

I did not read the details of exactly which log events are sent, so check SEB Server's documentation for that.

How the clients connect

SEB always makes the connection. The server never connects into a student's computer. In the Windows client the sequence is:

  1. Connection settings. The student starts SEB with a small configuration that holds the server address, an API discovery address, the institution, a client name and secret, and optionally an exam identifier. SEB Server generates this for you. The SEB Config Builder does not make it.
  2. Discover the API and log in. SEB loads the API from the discovery address and requests an access token with the client name and secret.
  3. Choose the exam. SEB asks which exams are available, and lets the student choose unless the configuration names one.
  4. Fetch the exam settings. SEB downloads the exam's configuration from the server and starts the exam with it. With SEB Server, the settings can come from the server rather than a file you upload to Moodle.
  5. Report during the exam. Pings, queued log entries, network and power status, and any hand-raising or instructions.

Where SEB Server can run

  • It is software you host yourself. I did not find a hosted service. Your central IT or learning-technology team may already run one.
  • Anywhere that runs Docker. The official setup guide says only Docker-based installs are currently supported. The server and its web interface are one Java container, with a separate MariaDB database. It runs on Java 21 and is licensed under MPL-2.0.
  • Sizing. The production guide uses the official MariaDB image with an nginx reverse proxy, and recommends about 4 cores, 32 GB of memory and 100 GB of disk. There is a lighter demo setup that needs only Docker and Docker Compose.
  • Reachable from students. Their SEB must be able to reach the server's address over HTTPS. For students at home that means a public address with a valid certificate. For lab rooms, an address on the university network may be enough.
  • Where the data sits. This affects your data protection position. Think about your own infrastructure or an approved UK or EU provider, retention rules and who can see recordings.

Firewalls, and what happens if SEB cannot connect

Each student computer needs an outbound HTTPS connection to the server (nothing inbound). Screen proctoring, if used, has its own address and may need its own rule. These requests come from SEB itself, not from the browser, so I believe the website allow-list does not apply to them, but this is my reading of the code and worth testing. I did not check whether SEB uses a system proxy for them.

Before the exam starts

  • If a request fails, SEB shows a dialog with Retry and Abort, and, if the configuration allows it, Fallback.
  • SEB keeps asking until a request succeeds or the student chooses, so a student behind a blocking firewall is stuck at that dialog.
  • Fallback starts SEB with the local start address and settings, without the server. The settings include a fallback password (sebServerFallbackPasswordHash), but I could not find where the Windows client checks it, so test that it is enforced before relying on it.
  • The number of retry attempts, the interval and the timeout are configurable.

During the exam

  • The exam keeps running. A failed ping only writes a warning to SEB's local log.
  • The student shows as disconnected on the server, and instructions such as lock or end do not arrive until the connection returns.
  • I did not check whether log entries from the gap are kept or lost.

Data protection

This is not legal advice. Recording web activity, window titles and especially screenshots is personal data processing, and screenshots can capture private content. In the UK you would normally need a lawful basis, a clear notice to students, a data protection impact assessment, minimal data collection and a retention period. Choose the least invasive option that meets your need: blocked-site messages and a local log may be enough, and screenshots are the heaviest choice. As with other monitoring, expect students to be anxious about it, so explain what is collected and why.

Before your first exam with SEB Server

  1. Ask IT to allow outbound HTTPS to the server from every network students will use.
  2. Test from a lab room, campus Wi-Fi, a home connection and any VPN.
  3. Decide whether fallback is allowed, and who holds the fallback password.
  4. Agree what invigilators do for a student who shows as disconnected.
  5. Complete your data protection review and tell students what is recorded.
  6. Run a practice session first. See the guide to secure exam environments for the wider picture.
